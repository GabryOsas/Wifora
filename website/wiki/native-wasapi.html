Native WASAPI Helper — wifora-audio.exe

A small optional C++20 helper that captures system audio via WASAPI loopback and hands it to the server without going through browser capture.

Why it exists

  • More robust than the browser path: bypasses getDisplayMedia quirks and GPU-driver dependencies.
  • Uses MMCSS "Pro Audio" to reduce starvation under CPU load, with an event-driven callback loop.
  • No network access whatsoever: it writes PCM to standard output, period.

Building

Via script (recommended)

powershell -ExecutionPolicy Bypass -File native\wasapi\build-wasapi.ps1

The script tries in order: CMake in PATH (+ copies the exe next to the script) → direct MSVC cl.exe build → MinGW g++ → recursive search of VsDevCmd/CMake inside Visual Studio. If no compiler is found it clearly tells you that you'll stay on the browser path.

Via manual CMake

cmake -S native/wasapi -B native/wasapi/build
cmake --build native/wasapi/build --config Release
# binary: native\wasapi\build\Release\wifora-audio.exe

Requirements: Windows, a C++20 toolchain (MSVC recommended), system libraries ole32, avrt, uuid.

Command line interface

wifora-audio.exe --list-devices          # lists active endpoints (ID + name)
wifora-audio.exe --stdout                # captures the default endpoint to stdout
wifora-audio.exe --stdout --device ID    # captures a specific endpoint

The "WFR1" binary protocol

Each stdout packet = fixed 32-byte little-endian header + interleaved Float32 PCM:

Offset Field Type Typical value
0 Magic ASCII[4] WFR1
4 Version UInt16 1
6 Channels UInt16 2 (stereo)
8 Sample rate UInt32 48000
12 Samples per channel UInt32 current frame size
16 Sequence UInt32 progressive counter
20 Reserved UInt32 0
24 Timestamp UInt64 samples since start

Key implementation notes: stdout is opened in binary mode (Windows text mode would turn 0x0A into 0x0D 0x0A, corrupting the PCM); samples are sanitized (NaN→0, clamp ±1); 16/24/32-bit int and float inputs are normalized and linearly resampled to 48 kHz with continuous state across packets; the SILENT flag produces explicit silence.

The full chain

[wifora-audio.exe] ──stdout WFR1──▶ [Node server]
   decoder with magic re-synchronization
   max-8 frame queue, drop-oldest under pressure
        │
        ▼ WebSocket ws://localhost:3975/native-audio?room=…&key=…
[raw Float32 frames (header already stripped)] ──▶ [Host page]
        │
        ▼ AudioWorklet 'wifora-native-pcm'
   ~2-packet startup buffer (~20 ms), ~60 ms ceiling,
   linear resample 48 kHz → device sample rate,
   underrun → intentional silence (no crackle)
        │
        ▼ same DSP chain + WebRTC as other paths
  • The relay accepts only the host tab: origin + room + hostKey are verified before upgrade.
  • One client per room: a new connection replaces the old one ("Replaced by a newer host connection").
  • Backpressure: if bufferedAmount exceeds 48 KiB the frame is dropped instead of accumulating latency.
  • Remote listeners still receive only Opus over WebRTC: native PCM never leaves the PC.

How to use it

  1. Compile (see above). The exe is searched in: WIFORA_WASAPI_HELPER env var → native/wasapi/wifora-audio.exe → native/wasapi/build/Release/wifora-audio.exe.
  2. On the host page press "Start with native WASAPI (experimental)" after creating the room.
  3. To point at a custom location: set WIFORA_WASAPI_HELPER=C:\path\wifora-audio.exe before starting the server.

Limitations: Windows only, and it captures the rendering endpoint (default or selected). It's not a microphone: it's for system output audio.
