Troubleshooting

Symptom → likely cause → fix. If your issue isn't here, open a GitHub issue with DEBUG logs attached.

No sound on the phone

  • iOS showing "Tap to enable audio"? Tap it: that's the browser autoplay block.
  • Did you tick "Share system audio" in the picker? Without it Wifora refuses to start (explicit error).
  • Volume: phone slider, in-app slider, Windows volume mixer.
  • Audio playing through another device (HDMI monitor/Bluetooth)? Change the Windows output: the active endpoint's mix is what gets streamed.

"Nessuna trasmissione attiva per questo codice." (No active broadcast for this code)

  • The broadcast was stopped or the host dropped beyond the 8 s grace: restart it from the PC to regenerate QR/code.
  • Wrong code: it's 8 uppercase characters, with no O/I to avoid 0/1 confusion.

"La stanza ha già raggiunto il limite di ascoltatori." (Room listener limit reached)

Limit hit (default 5). Kick a device from the host or raise the cap: set WIFORA_MAX_LISTENERS=8 and restart (max 32; beyond ~10 on 2.4 GHz it's the Wi-Fi that suffers, not Wifora).

"Port already in use" / port 3975 busy

  1. Open the Control Center → Free Port, or run Termina-Wifora.bat.
  2. Alternatively change port (CLI "Change Port", or PORT=8080 npm start).

The phone can't reach the PC

  • Same Wi-Fi? Some routers split 2.4/5 GHz into separate "guest" SSIDs: put both devices on the same one.
  • AP isolation (guest/hotel networks): clients can't talk → use the PC's hotspot.
  • Firewall: allow Node.js on private networks; test with Test-NetConnection PC-IP -Port 3975.
  • VPN active on the PC: can reroute traffic — try disabling it.

The QR doesn't load

Browser extensions blocking external images, or a filtered /qr endpoint. The room code + manual URL shown under the QR always work.

Audio drifts out of sync over time

  • Correct behavior under network stress: ANAE drops tiers and the jitter buffer grows to 35–50 ms to protect you.
  • Move to 5 GHz or closer to the router; on clean Wi-Fi you'll be back to 22 ms and ±1–2 ms sync.
  • Persistent huge drift? Restart the broadcast: clock-sync starts from zero.

Occasional clicks/pops

Real packet loss (see the loss % in the UI). FEC repairs single holes; beyond a few percent you need better signal: 5 GHz, fewer walls, or the Eco profile.

Chrome doesn't show the "Share audio" checkbox

  • Update Chrome/Edge (a recent version is needed on Windows).
  • Select the Entire Screen tab: the option may be missing for single tabs/apps.
  • Firefox/macOS/Linux: browsers don't support system-wide capture there (use the native WASAPI path on Windows).

iOS: no audio after screen lock

Returning to the foreground, Wifora resumes automatically (AudioContext resume + Wake Lock). On LAN HTTP Wake Lock is unavailable (needs a secure context): the toggle stays off and iOS may sleep the screen — install the PWA from the Home Screen for the best experience, or enable HTTPS.

I reloaded the host page: did I lose the room?

No: credentials live in sessionStorage (12 h) plus an 8 s server grace. You re-enter the same room with the same code/QR. Only an explicit Stop closes everything.

"wifora-audio.exe not found" / WASAPI won't start

  • Compile first: build-wasapi.ps1 or CMake (guide).
  • Custom path: WIFORA_WASAPI_HELPER variable.
  • Don't want to compile? Ignore it: the browser path works without.

Where are the logs?

  • The server terminal (level settable via LOG_LEVEL=DEBUG).
  • CLI menu → live dashboard (refreshed every 1.2 s).
  • Control Center → status/logs section (/api/logs).

Full reset

Termina-Wifora.bat          # stops processes, frees 3975+3976
del wifora.config.json      # port back to default
# host browser: clear sessionStorage (F12 → Application)
